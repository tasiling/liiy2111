# 噗浪・蓋樓台(聊解室 → 噗浪蓋樓,擁有者提供 plurk-tower.html 原型,2026-08-02)

## 範圍與定位

依擁有者驗證過的 plurk-tower.html 原型實作,位置在聊解室的「噗浪蓋樓」頁籤
(`/plurk`,第 6 個頁籤,與今日工作/日上三更/五光行旅/共振會/服務並列)。三個
子頁(發文佇列/日上三更/範本)、長文分樓規則(心乘光、命運籤詩各有專屬 parser,
其餘走 `---` 斷樓)、逐樓複製流、字數檢查(360 字上限提示)、排程到點亮金邊、
範本建立與編輯、由版型產生骨架——這些原型已驗證的部分照做,不重新設計。視覺
沿用 `.dojo` CSS token,新增的元件類別全部加上 `.plurk` 範圍限定(見
`app/dojo.css`),不影響其他頁面。

日上三更版型卡實際上是 10 張(晨光 2、日光 7、夜光 1),擁有者指示文寫「九張」,
判斷是敘述時的約略記憶,不是規格要求——以原型 `SANKO` 常數的實際內容為準,
10 張皆已搬入 `lib/plurk/data.ts`。

## 與日上三更(/sanko)的關係

依指示這階段不串接,各自獨立運作。`lib/plurk/data.ts` 的 10 張版型卡是原型
`SANKO` 常數的原樣搬移,與 `lib/dojo/methods.ts` 的「八方法規格」有 8 個方法
重疊,但這裡另外多兩張(xincheng 心乘光・週指引、yeguang 夜光・服務陪伴)且
每張多帶噗浪蓋樓專用欄位。刻意不與 `lib/dojo/methods.ts` 共用同一份資料,兩邊
用途不同,比照本專案已有的先例(見 `docs/schema/日上三更指令產生器.md`)。

## 不做(依指示)

不接噗浪 API、不做自動發佈。排程只是「預先寫好＋到點提示」(卡片到點自動亮
金邊),沒有任何自動貼文的程式路徑。

## 儲存架構(2026-08-02 擁有者裁決,已實作)

範本與草稿都存 **DB-14 知識庫**,不新增任何欄位或選項值:

- 來源 = 原創、狀態 = 存貨、核可狀態 = 免審(皆既有選項)
- 標題前綴區分類型,查詢時用 `starts_with` 篩選(`lib/notion/schema.ts` 的
  `PLURK_TEMPLATE_TITLE_PREFIX`/`PLURK_DRAFT_TITLE_PREFIX`):
  - 範本:`噗浪範本-{名稱}`
  - 草稿:`噗浪草稿-{標題}-{建立日}`(標題部分每次存檔都用當下主噗內容重新
    推導,方便在 Notion 瀏覽時看到最新內容;建立日固定不變)
- 排程時間、樓層內容、發布狀態、方法代號(method)、來源範本名稱(tplName)
  一併序列化存進「內容」欄——結構化文字格式見 `lib/plurk/notionFormat.ts`
  (`encodePlurkContent`/`decodePlurkContent`):第一段是 JSON 一行的
  metadata,之後接主噗、再接各樓文字,用一個不會出現在噗浪貼文裡的標記字串
  分隔。metadata 損毀(例如被人手動編輯壞掉)時容錯退回空 meta,不擋讀取。

草稿要存成範本時,呼叫端(`app/plurk/page.tsx` 的 `saveAsTpl`)直接在同一個
DB-14 新建一筆範本,不用跨庫搬家——原本的草稿仍保留,語意是「另存一份」不是
「轉換」,照原型行為。

### 技術修正:`richTextProp()` 補上長文字切塊

實作時發現 Notion API 對單一 rich_text 區塊的 `text.content` 有 2000 字元硬
限制,而噗浪蓋樓批次貼文動輒上萬字(如擁有者提過的「一批 14 篇」)。既有的
`lib/notion/properties.ts` 的 `richTextProp()` 只把整段文字塞進一個區塊,長
內容會被 API 拒絕或截斷。已修正為自動切成多個 ≤2000 字的區塊——讀取端
`readRichText()` 原本就會把多個區塊的 `plain_text` 串接讀回,這裡只是補上
對稱的寫入端切塊,對既有所有呼叫端(內容遠短於 2000 字)是無感的相容修正,
不影響任何既有功能。

### 前端存檔節奏

文字類編輯(主噗/樓層內容、範本名稱)採 1.2 秒防抖自動存檔,停止輸入後才送出
`PATCH`,避免每個按鍵都打 Notion API;結構性動作(新增草稿/範本、刪除、標記
完成、加樓/刪樓、排程時間變更)即時送出,不需要使用者手動按存檔按鈕。

### 「日上三更」10 張版型卡的 parser 對應

分樓規則(心乘光、命運籤詩的專屬 parser)原本用範本的固定 id(`tpl-xcg`/
`tpl-fate`)判斷,現在範本存進 Notion 後 id 是動態指派的頁面 id,已改成用
範本的 `method` 欄位(`xincheng`/`qianshi`,建立範本時就會寫入且不會變)判斷,
不受 id 變動影響。

### 兩個預設範本不再自動建立

原型的「心乘光・週指引」「聊解時間・命運籤詩」兩個預設範本,原本在瀏覽器
localStorage 是隨頁面載入就存在的假資料;現在範本要寫進 Notion,不應該讓
App 在使用者沒有任何動作的情況下就自動寫入資料。改為:「範本」子頁在範本
清單為空時顯示「建立預設範本」按鈕,使用者按下去才會真的建立這兩筆——是
明確的使用者動作,不是背景靜默寫入,符合本專案一貫「App 不擅自動作」的原則。

## 若之後發現內容欄裝不下或查詢困難

依擁有者指示,先用現有結構(DB-14 + 序列化內容欄)跑一輪;若實際使用後發現
單筆內容真的超出合理範圍,或依標題前綴查詢在資料量變大後變慢/不好用,回報
後再議是否需要獨立資料庫。

## 已知的視覺落差

`.pv` 內文裡的噗浪表符(emos.plurk.com 圖片網址)沿用原型的 CSS,只設定
`height:16px`,沒有設定 `width`。正常網路環境下圖片能載入,不影響版面;但若
單張圖片因為網路問題載入失敗,瀏覽器可能把破圖佔位框撐到接近版面寬度,造成
該行版面被撐高。這是原型 CSS 本身就有的行為(原型也只設定 height),不是本次
移植新增的落差,故未額外加寬度限制——盡量真實接近原型驗證過的樣式。
