## 儲存現況:暫時用瀏覽器 localStorage(TEMP,兩個問題需要擁有者裁決)

前端(三個子頁、分樓、骨架產生、複製流、排程判斷)已經完整可操作,但目前用
`lib/plurk/store.ts` 存在瀏覽器 localStorage(key: `plurk-tower-v1`),不是最終
形態。原因是委派書本身對「範本」存放處要求「先回報建議方案再實作」,而「草稿」
雖然委派書已指示「可沿用 DB-04 的『草稿』欄位」,但實際核對 DB-04 的既有規則後
發現這個指示會撞到兩個既有限制,需要先跟擁有者確認怎麼處理,不能自行決定架構。

### 問題一:範本(templates)存放處——委派書明確要求先回報建議方案

**建議方案:沿用 DB-14 知識庫,不需要新增任何欄位或選項值,不需要你批准 schema
變更。**

具體做法:
- 來源 = 原創(既有選項)
- 狀態 = 存貨(既有選項,語意上剛好符合「已備妥、等被用」的範本狀態)
- 核可狀態 = 免審(來源=原創的預設值,依委派書規則自動成立)
- 標題 = 「噗浪範本・{範本名稱}」前綴,供在 DB-14 眾多知識條目中快速辨識與篩選
- 內容(長文字欄)= 主噗與各樓文字用分隔符序列化存成一筆長文字(比照「草稿」
  欄位已經是「主文與解析包都存這裡」的先例,同一種處理方式)
- 若範本源自某個日上三更版型卡,方法代號(如 xincheng)寫進標題括號或衍生紀錄
  欄,不需要新增獨立欄位

這完全符合產線 A 委派書〇之 7「能以資料列承載者,不擴充欄位」的既定原則(語氣
指引就是同一套做法的先例),也不會動到任何封閉清單。

替代方案(需要你批准):新建一個獨立的「噗浪範本庫」,可以有更乾淨的專屬欄位
(方法代號、樓層數各自成欄),但需要你在 Notion 新建資料庫並批准新 schema。

### 問題二:草稿(drafts)——委派書指示沿用 DB-04,但撞到兩個既有規則

DB-04 抽牌明細有兩個對「噗浪蓋樓草稿」這個用途不合身的既有限制:

1. **「所屬 Session」是必填關聯**(委派書原文:「必填」)。噗浪蓋樓的草稿(尤其
   原型的「空白新增」與「長文分樓」兩種起手式)通常不對應任何真實的抽牌
   Session——沒有牌卡、沒有生產動作,純粹是一篇要發到噗浪的貼文。
2. **DB-04 沒有「排程時間」欄位**,「對應日期」只到天,原型需要精確到時分才能
   判斷「到點亮金邊」;「明細狀態」的四個選項(待產出/待審核/已產出/已交付)
   語意上也對不上噗浪蓋樓這邊單純的「草稿/已排程/已發佈」三態(這三態沒有
   「審核」的概念,是純粹的發文進度)。

在委派書「不動 Notion schema:不新增欄位、不改選項、不建資料庫」與「欄位表為
封閉清單,認為有缺漏時停下回報,不得自行補充」的規則下,不能自己決定怎麼處理,
提出三個選項供你裁決:

**選項 A(建議):噗浪蓋樓草稿另建一個獨立的小資料庫。**
不受 DB-04「所屬 Session 必填」與「明細狀態」四階語意的綁定,乾淨對應原型的
資料形狀(草稿編號、主噗內容、樓層內容、排程時間、狀態三態、選填關聯回
DB-04 明細供未來串接用)。需要你在 Notion 新建資料庫並批准。

**選項 B:繼續掛在 DB-04,但需要新增必要欄位。**
新增「排程時間」(datetime)欄與噗浪蓋樓專用的狀態選項;「所屬 Session」必填
的問題用一個你指定的「噗浪蓋樓」佔位 Session 承接所有噗浪草稿(這筆 Session
本身不對應任何真實抽牌動作,只是為了滿足關聯必填)。需要你在 Notion 動幾個
欄位並批准,且會讓 DB-03/DB-04 出現非典型用途的資料列。

**選項 C:草稿也維持先用瀏覽器暫存,晚點再決定。**
現況就是這個做法——三個子頁的操作邏輯已經完整可用,可以先實際操作、體驗
流程,之後再定案怎麼接 Notion(比照日上三更指令產生器第一輪的做法)。

擁有者「草稿一律存 Notion,不存 localStorage」的硬性原則是針對日上三更指令
產生器明確講的;是否同樣套用到噗浪蓋樓,連同上述選項一併請你決定。決定後
只需要替換 `lib/plurk/store.ts` 的實作,`app/plurk/page.tsx` 的其餘邏輯不受
影響。

## 已知的視覺落差

`.pv` 內文裡的噗浪表符(emos.plurk.com 圖片網址)沿用原型的 CSS,只設定
`height:16px`,沒有設定 `width`。正常網路環境下圖片能載入,不影響版面;但若
單張圖片因為網路問題載入失敗,瀏覽器可能把破圖佔位框撐到接近版面寬度,造成
該行版面被撐高。這是原型 CSS 本身就有的行為(原型也只設定 height),不是本次
移植新增的落差,故未額外加寬度限制——盡量真實接近原型驗證過的樣式。
