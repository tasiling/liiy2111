# 收光三選項與居所接續(資料邏輯規格 v1.0,2026-08-03)

## 前情:規格書第三章作廢

原規格書提案為此新增三個欄位(`closingChoice`/`carryToDate`/`carryNote`),並引用
《網站規格書 v0.9》第 4.2 節的 `sourceType`/`traceLevel`/`traceStatus` 資料模
型。經回報確認,這組欄位是規劃文件的設計提案,主站從未實作,委派書誤把規
劃模型當成現況引用。**擁有者裁決:不新增任何欄位**,收光紀錄改為沿用主站
現行 `DojoEntry` 的既有欄位語意(`space`/`kind`/`title`/`note`/`date`)。原提
案的三個新欄位全數作廢,「帶回明天」的接續判斷改用「昨天的收光紀錄」+
「title === 帶回明天」直接判斷,不需要 `carryToDate`。

## §3.2 Notion 對應裁決

沿用方案 A:DB-14 知識庫 + 標題前綴,比照噗浪・蓋樓台先例,零 schema 異
動。標題格式 `收光紀錄-YYYYMMDD`,一天一筆,若當日已有紀錄則覆蓋(擁有者
可能改變主意),不累積多筆。內容欄(`內容`)序列化一個 JSON:
`{space:"closing", kind:"收光", title:"帶回明天"|"暫且放下"|"直接收光",
note?, date}`。見 `lib/closing/notionFormat.ts`。

## B2/B3 裁決:本輪跳過

居所接續卡片原規格有三個系統自動推導來源(B1 日上三更、B2 織光堂、B3 野
採)。排查後確認:織光堂、野採兩個場域目前沒有任何持久化資料模型(沒有作
品狀態、下一步欄位、提問建立時間追蹤、帶往關聯),B2/B3 建立在不存在的地
基上。擁有者裁決本輪跳過,居所接續卡片改為只有 Source A(帶回明天)+
Source B1(日上三更待產出)兩個來源,B2/B3 留到織光堂與野採真正動工那一輪
再裁決資料模型。

## 本輪範圍與實作

### ① `POST /api/closing`(收光三選項)

`app/api/closing/route.ts`:

```
Body: { choice: 'carry' | 'pause' | 'close', note?: string }
```

- 三個選項都**不改動**任何一筆痕跡(`useDojo()` 的 `entries` 完全不碰),只
  是建立/覆蓋當天在 DB-14 的一筆收光紀錄(§0.1)。
- `choice='carry'` 時,`note` 選填,空字串一律存成 `undefined`(區分「沒
  寫」與「寫了空白」)。
- 用 `findKnowledgeEntryByTitle()` 精確比對「收光紀錄-{今天}」,存在則
  `updateKnowledgeEntry`,不存在則 `createKnowledgeEntry`——以最後一次選擇為
  準,不累積多筆(§四)。

`app/closing/page.tsx`:「暫且放下」「直接收光」點下去直接送出;「帶回明
天」多一步——展開一句話輸入框(可留空、可取消),按「帶回明天」確認才送
出。三者送出成功後都播放低刺激收光動效(`.dojo .settle`,800–1200ms 淡入淡
出,對應 CSS `dojo-settle-fade` 動畫,實際設定 1000ms),再導回居所。

### ② 居所接續卡片(Source A + Source B1)

`app/api/closing/continuations/route.ts`(GET):

- Source A:用 `findKnowledgeEntryByTitle()` 查「收光紀錄-{昨天}」,解碼內
  容後若 `title === '帶回明天'`,取 `note`(有值則顯示,否則顯示預設文字
  「昨天你想把這件事帶到今天」),最多 1 張。
- Source B1:重用既有的 `listPendingDetails()`(DB-04),過濾
  `明細狀態=待產出`(空值視同待產出,既有的防禦性 fallback 規則)且
  `對應日期<=今天`,依日期升冪排序,補滿剩餘名額——最重要的一項排最前面
  (規格 §2.1)。卡片文字有更次值時顯示「{M/D} 的 {更次} 還沒發」,沒有更
  次值(非批次系統的舊式明細)則顯示「{M/D} 有一篇還沒發」,不顯示明細編
  號。
- 硬性限制:最多 3 張、不足不補空位、零張時 `app/page.tsx` 整個「回到哪
  裡」區塊不渲染(不是既有「接續中的事」空狀態那種顯示空文字的做法)、不
  顯示總數或逾期天數、文字中性(「還沒發」「想帶到」,不使用催促語氣)。

`app/page.tsx`:新增「回到哪裡」區塊,位置在「今天要做的事」與「接續中的
事」之間——這是一個新區塊,不覆蓋既有的「接續中的事」(那個區塊顯示的是
使用者自己在各場域留下的 `DojoEntry` 痕跡,跟這裡的系統推導接續卡片是兩件
事,兩者並存)。Source B1 的卡片可點擊,跳轉到 `/sanko?detailId={id}`,沿用
「總覽台行事曆」修正時已建立的捲動＋標示機制;Source A 的卡片是純文字,不
可點擊(沒有明確的跳轉目標)。

## 紅線檢查(§五)逐條核對

- 收光不改動任何一筆痕跡的 `traceStatus`(此處對應 `DojoEntry`,`entries` 完
  全未被 `POST /api/closing` 觸碰)——✓
- 「暫且放下」「直接收光」行為完全相同,只有 `choice` 值不同——✓
- 沒有收光的日子系統不做任何事、不提供補收光——✓(沒有任何背景任務、排程
  或「補做」入口)
- 居所不顯示待辦總數、逾期天數、完成率——✓(卡片文字純敘述句)
- 接續卡片不足 3 張不補空位,零張整區不顯示——✓
- 程式碼中不存在任何連續天數的計算邏輯——✓(全站 grep 確認)

## 驗證

用 Playwright 對照《收光三選項與居所接續 v1.0》§六逐條測試(mock `/api/
closing`、`/api/closing/continuations`,因沙盒環境無真實 Notion 憑證):

- 「暫且放下」「直接收光」點擊後送出的 body 分別為 `{"choice":"pause"}`
  `{"choice":"close"}`,顯示收光動效後約 1 秒導回居所。
- 「帶回明天」填一句話送出 `{"choice":"carry","note":"..."}`;留白送出
  `{"choice":"carry","note":""}`(伺服器端轉存為 `undefined`)。
- 居所 mock 零卡片時,「回到哪裡」標題完全不出現;mock 兩張卡片(Source A
  文字 + Source B1「8/3 的 日光 還沒發」)時皆正確顯示,點擊 B1 卡片正確跳
  轉到 `/sanko?detailId=...`。
- 全站 grep 確認無 `traceStatus`/`sourceType`/`traceLevel`/連續天數等未裁決
  概念被引入。
