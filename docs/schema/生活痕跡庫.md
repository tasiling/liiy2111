# 生活痕跡庫(補充裁決04/05,2026-08-05)

依《委派書補充裁決 05｜痕跡持久化》的實作順序,本文件記錄第2–5項的完整交
付(第2項先交付過一次,第3–5項這次一次做完再回報,依擁有者指示「做到居所
能實際顯示為止再叫你」)。

## 一、資料庫

擁有者建庫,App 只讀寫不建庫(比照 DB-17/DB-18 先例)。實際欄位經
`notion-fetch` 讀取驗證,非憑記憶假設:

| Notion 欄位 | 型別 | 說明 |
|---|---|---|
| 標題 | title | |
| 內容 | rich_text | |
| space | select | practice/forage/weaving/liaojie/dao/closing |
| sourceType | select | practice/forage/work/service/archive/rest/alchemy |
| traceLevel | select | daily/accumulated/permanent(描述:「permanent 為入藏,是成為行光牌的前提」) |
| traceStatus | select | 一般/收納/隱藏 |
| viewCount | number | 描述:「回看次數,達 3 次自動升為 accumulated」(門檻本身第4項才實作) |
| 最後動靜時間 | date | 描述:「建立、回看、標記都要更新;淡去以此即時計算」 |
| 頻率 | number | 霍金斯量表 0–1000,手動填,可留空 |
| 強度 | number | 1–10,手動填,可留空 |

`lib/notion/schema.ts`:`DATA_SOURCES.DB19_生活痕跡庫`。

## 二、查詢限縮(補充裁決05 §2.1 硬規則)

不得每次撈全部痕跡再於程式端過濾——條件寫在 Notion filter 裡。

### `listRecentTraceCandidates()`(上區候選)

只取 `traceLevel=daily` 且 `頻率`/`強度` 皆未填(標記過的痕跡屬於下區,見
補充裁決04 §2.2)、且「最後動靜時間」落在查詢窗口內(`TRACE_QUERY_WINDOW_
DAYS = 10`)的候選。

**查詢窗口(10 天)不是淡去門檻(7 天)**——這裡只負責把候選集合縮小到一
個安全範圍,真正「是否已淡」的 7 天比較留給讀取結果之後的顯示邏輯(補充
裁決04 §1.1:淡去是算出來的,不寫入任何狀態欄位),屬於實作順序第3項,
本輪未做。

### `listPersistentTraces()`(下區候選)

`traceLevel=accumulated` OR `traceLevel=permanent` OR `頻率`有值 OR
`強度`有值——四個條件用 `or` 併查,一次查詢就是最終候選集合,不限張數
(補充裁決04 §2.2)。

兩個查詢分開下,不合併成一次全撈,符合硬規則。

## 三、寫入

`lib/notion/mutations.ts`:

- **`createTraceEntry(params)`**:建立時 `traceLevel`/`traceStatus`/
  `viewCount` 一律寫入初始值(daily/一般/0),`最後動靜時間`寫入當下——
  建立本身就是一次動靜。頻率/強度建立當下一律不填(測頻是後續獨立動
  作)。
- **`markTraceMeasure(id, {頻率?, 強度?})`**:標記頻率/強度本身也是一
  種動靜,只寫入這次真的動過的欄位,同時更新「最後動靜時間」。標記之
  後這筆痕跡會落入下區的判斷,交給 `listPersistentTraces()` 的查詢條
  件處理,這裡只負責寫值。
- **`registerTraceView(id)`**(第4項):回看——重新計時 7 天 + 回看次數
  `viewCount` +1;累積到門檻(`TRACE_ACCUMULATE_VIEW_THRESHOLD`,見下)
  且目前是 `daily` 才自動升級為 `accumulated`。已經是 `accumulated`/
  `permanent` 的只單純累加次數與時間,不重複判斷升級。

## 四、淡去邏輯(第3項)

新檔 `lib/trace/rules.ts`:

- `TRACE_FADE_DAYS = 7`:淡去門檻,獨立常數,不散落在各處當 magic
  number。
- `isFaded(最後動靜時間, now?)`:純函式,現在時間減最後動靜時間 ≥ 7 天
  即已淡。**不寫入任何欄位、不跑排程**——這是唯一判斷「是否已淡」的地
  方,在讀取結果之後、顯示邏輯那一步才算(補充裁決04 §1.1)。
- `filterUnfaded(traces[])`:套用在 `listRecentTraceCandidates()` 撈回
  的候選上,只留下未淡去的。查詢層(`TRACE_QUERY_WINDOW_DAYS=10`)只是
  把候選縮小到安全範圍,兩層職責分開,已在委派書05 §2.1 的回報裡說明
  過。
- 已用固定時間戳的單元測試驗證邊界:6 天前=未淡、剛好 7 天前=已淡、8
  天前=已淡、`最後動靜時間` 為 `null`=視同已淡(防禦性)。

## 五、回看次數計數與 traceLevel 自動升級(第4項)

`lib/trace/rules.ts`:`TRACE_ACCUMULATE_VIEW_THRESHOLD = 3`——委派書原文
「門檻 3 次,須為可調設定值」,這個具名常數就是那個可調設定值,之後要
調整只改這一行。

實際升級邏輯在 `registerTraceView()`(見上一節),由 `PATCH
/api/traces/[id]/view` 呼叫。

## 六、居所兩區呈現(第5項)

### 建立/標記怎麼連到 DB-19

`DojoEntry` 新增 `traceId?: string`(`lib/dojo/constants.ts`)。

- `lib/dojo/store.tsx` 的 `addEntry()`:建立本地 entry 的同時,背景呼叫
  `POST /api/traces` 寫進 DB-19(失敗靜默,不擋 UI),成功後把回傳的
  Notion page id 補回該筆 entry 的 `traceId`。**私人項目
  (`privacy==="私人"`)完全不建立痕跡**——DB-19 沒有 `privacy` 欄位,
  無法在讀取端過濾私人內容,唯一能維持「居所不顯示私人項目」既有保護
  (三方協作規格書既有規則)的做法是私人項目一開始就不寫進 Notion。
  **直接後果**:目前一律 `privacy="私人"` 建立的路徑(`app/timer/
  page.tsx` 的 `finishTimer()`)不會產生任何痕跡紀錄,計時器完成的紀
  錄目前不會出現在居所兩區。這是這個保守選擇的直接結果,不是遺漏——
  如果這不是您要的行為,麻煩告訴我,調整方式是幫計時器產生的紀錄開放
  非私人選項,或重新評估 DB-19 要不要補一個 privacy 欄位。
- `setEntryFreq()`/`setEntryIntensity()`:只有在**設定真的數值**(不是
  清除)且該筆 entry 已經有 `traceId` 時,才背景呼叫 `PATCH /api/
  traces/[id]/measure` 同步進 DB-19。**清除標記(設回 `null`)刻意不同
  步**——「取消標記後這筆痕跡是否要重新開始淡去」沒有被裁決過,本輪
  不猜測,只同步「設定」這個方向;清除目前仍然只影響本地/收光復盤畫
  面,不會讓已經進了下區的痕跡退回上區。

### 新增 API

- `POST /api/traces`:建立(`addEntry` 背景呼叫)。
- `PATCH /api/traces/[id]/view`:回看(居所卡片點擊呼叫)。
- `PATCH /api/traces/[id]/measure`:標記(`setEntryFreq`/
  `setEntryIntensity` 背景呼叫)。
- `GET /api/traces/home`:居所兩區查詢,回傳
  `{recent: TraceCard[], persistent: TraceCard[]}`。**回傳的卡片刻意不
  含頻率/強度數值**——三方協作規格書 v1.3 §2.3 明訂「測頻不得在居所以
  任何形式顯示」,這是既有紅線(`EntryCard` 元件既有的 `showFreq=
  {false}` 慣例),這裡從資料源頭就不给,不是靠前端不渲染。

### `app/page.tsx`

原本的「接續中的事」(`entries.filter(privacy!=="私人").slice(-3)`,純
前端記憶體,重整就消失)整段換成兩個新區塊,改讀
`GET /api/traces/home`:

- **上區「最近的痕跡」**:`recentTraces.length===0` 時整區不顯示,不出
  現空狀態文字。卡片是按鈕,點擊即觸發 `PATCH /api/traces/[id]/view`
  (回看)——安靜地發生,不彈確認、不顯示任何時間/次數。
- **下區「留著的」**:`persistentTraces.length===0` 時整區不顯示。用原
  生 `<details>/<summary>` 實作可摺疊,標題「留著的」**不帶任何數字**。

**下區預設收合/展開尚未經您正式拍板**(補充裁決05 §五仍列為未裁決)。
這裡先用我方之前回報過的建議選項A:比照全站既有的 `<details>/
<summary>`、預設收合、標題維持中性文字。選這個純粹是「先讓居所能實際
顯示、供您驗收」的權宜選擇,不是替您做了決定——若您驗收時想要選項B
(預設展開)或選項C(加不帶數字的提示點),都只是 `app/page.tsx` 裡這
一小段的區域性調整,不影響其他任何部分。

兩區都沒有東西時,兩個區塊都不顯示,不出現任何空狀態文字(補充裁決04
§五驗收項8)。

- **尚未做端對端的真實 Notion 讀寫驗證**:這個沙箱環境沒有 App 自己

  復盤測頻標記這筆的頻率或強度 → 應該從上區移到「留著的」下區。我會
  用唯讀查詢比對 DB-19 的實際內容確認每一步都對得上。
