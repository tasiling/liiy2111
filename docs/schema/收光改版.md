## 背景:同日重複收光靜默覆蓋,是規格的錯不是實作的錯

《收光三選項與居所接續》v1.0 訂的規則是「一天一筆,當日已有紀錄則覆蓋」
——這條規則本身沒有考慮「使用者可能忘記自己今天已經收過光,再點一次會
把原本的選擇連同帶回的日期、寫的話一起蓋掉,沒有任何提示」。這是規格層
級的缺口,補充裁決03 §二正式指出並要求補上確認機制。

## 一、`GET /api/closing/today`(新增)

`app/api/closing/today/route.ts`:查今天是否已有收光紀錄,回傳精簡描述
(不含 `sourceType`/`traceLevel` 等呼叫端用不到的地基欄位):

```ts
{ existing: { title, note, carryToDate } | null }
```

## 二、`app/closing/page.tsx`:送出前確認覆蓋(§3.1)

進頁面時呼叫上述端點,存進 `existingToday`。三個送出入口(暫且放下/寫下
今天的直接按鈕、帶回流程最終的送出按鈕)都改呼叫 `requestSubmit()`而不是
直接送出:

- `existingToday` 為 `null`(今天還沒收過光):直接送出,行為不變。
- `existingToday` 非空:先跳出確認區塊,說明「今天已經收過光了(<今天既
  有的標題>),要用新的取代嗎?」,兩顆按鈕:
  - **保留原本的**:不呼叫 `POST /api/closing`,直接回居所——維持委派書
    「不得靜默覆蓋」的核心要求,也不得「什麼都不做又留在原地」,回居所
    是唯一合理的落點。
  - **取代**:照原本的送出邏輯執行。

伺服器端(`POST /api/closing`)刻意維持「呼叫就寫入」不變——是否要提示覆
蓋是前端的職責,這點在 route.ts 的註解裡有記錄,比照全站既有的
`window.confirm()` 類客戶端確認慣例(例如日上三更批次刪除),沒有在伺服
器端另外擋「已存在」的情況。

## 三、送出成功後的回饋文字(§3.2,草稿文案)

`lib/closing/notionFormat.ts` 新增 `feedbackText(choice, carryToDate)`,
在 800–1200ms 的低刺激收光動效同時顯示一句話,取代原本固定的「已收光」:

| 選項 | 草稿文案 |
|---|---|
| 帶回明天 | 「這件事會在 M/D(週X)出現在居所。」 |
| 寫下今天 | 「今天寫下的內容已經存下來了。」 |
| 暫且放下 | 「今天到此結束,不會留下任何待辦。」 |

三句話都只描述系統剛剛做的事,不評價這一天過得如何,不含鼓勵/關心/暗示
「有沒有產出」的措辭——依委派書§3.2 硬性規則。**文案是草稿,實際文字由
擁有者核定**,核定後只需要改這一個函式,不牽動任何邏輯。

## 四、「直接收光」更名「寫下今天」(§3.3)

原名的語意是「跳過、什麼都不做」,與這個選項現在要承載的「寫下今天」動
作相反。更名範圍:

- UI 上的按鈕文字與寫入 Notion 的 `title`:`ClosingChoiceTitle` 從
  `"直接收光"` 改為 `"寫下今天"`。
- API 的 `choice` 值:從 `"close"`(已名不符實)改為 `"journal"`。

**存量資料不遷移**:DB-14 裡任何用舊字面「直接收光」寫入的舊紀錄,
`decodeClosingContent()` 原樣讀出、不會壞掉——委派書只要求「不得因為讀
到舊字串而壞掉」,沒有要求把歷史紀錄的文字內容也一併改掉。

## 五、驗收(Playwright,mock `/api/closing`、`/api/closing/today`)

## 七、3.4 「寫下今天」展開七題(擁有者裁決後動工)

`lib/journal/notionFormat.ts` 定義 `JOURNAL_QUESTIONS`(七題,含 key/
label/group)、`journalRecordTitle()`(比照收光紀錄「日記-YYYYMMDD」格
式)、`normalizeJournalAnswers()`(七題一律正規化成字串,沒填的變空字
串)、`hasAnyJournalAnswer()`(判斷這次送出有沒有真的寫東西)。

`app/closing/page.tsx`:點「寫下今天」不再立即送出,改為展開
`JournalQuestionsPanel`——晨間組、夜間組各四/三題**一次全部列出**,每題
一個 `<textarea>`,placeholder 統一「選填」,**不顯示已填幾題、還剩幾
題、進度條或任何完成度**,也**不要求先選「今天要寫多少」**(委派書
§3.4 硬規則,逐條核對過)。「完成,送出」按鈕送出 `{choice:"journal",
journal:{...}}`,七題全空也能送出(硬規則:全部可留空)。

## 八、3.5 「帶回明天」也提供日記入口

`app/closing/page.tsx` 的帶回流程:選完日期、填完(或略過)一句話之
後,新增一個決定點——「要不要順便寫下今天?不想寫可以直接結束。」兩個
按鈕:「寫日記」展開同一個 `JournalQuestionsPanel`,「不寫,直接帶回」
沿用原本的送出邏輯(不帶 `journal` 欄位)。

## 九、`POST /api/closing` 寫入日記(3.4/3.5 共用)

新增 `journal?: JournalAnswers` 參數。**只有前端真的開過日記面板且至少
寫了一題**(`hasAnyJournalAnswer(journal)` 為真)才呼叫
`upsertJournalEntry()` 動 DB-18——沒開日記面板(`journal` 整個沒出現在
request body)或開了但全部留白,都不建立/更新日記紀錄,不在庫裡堆空白
列。

`lib/notion/mutations.ts` 的 `upsertJournalEntry(dateISO, answers)`:比
照收光紀錄「一天一筆,當日已有紀錄則覆蓋」——用標題「日記-YYYYMMDD」找
既有紀錄,有就整批覆蓋七個欄位(`normalizeJournalAnswers` 正規化過,沒
填的欄位明確寫入空字串,不是保留舊值的部分合併),沒有就連同標題/日期
一起新建。是否要覆蓋、要不要提示使用者——比照 §3.1 的既有邏輯,同一次
收光動作裡日記與收光紀錄綁在同一個確認閘門下,不另外為日記單獨加一層
確認對話框(委派書沒有要求,自行加會是「自行發明產品邏輯」)。
