原委派書把 `DojoEntry` 當成有持久化的資料表,引用「DB-04 加欄位後 17 筆舊
資料變空值」作為存量資料風險的類比。經回報+擁有者確認(補充裁決01§〇):

示範資料,沒有真的在累積的存量資料。委派書原本規劃依賴 `DojoEntry` 持久化

在這個現況下建了也不會成立,已從本輪範圍移除,延後到痕跡真正持久化的那
一輪。

## 本輪做的四件事

### 一、`DojoEntry` 新增四個地基欄位

`lib/dojo/constants.ts`:

```ts
export type SourceType = "practice" | "forage" | "work" | "service" | "archive" | "rest" | "alchemy";
export type TraceLevel = "daily" | "accumulated" | "permanent";
export type TraceStatus = "一般" | "收納" | "隱藏"; // 值域裁決(補充裁決01之2)
```

四個新欄位在 `DojoEntry` 型別上設為**必填**(不是 optional)——委派書步驟
二「必做:建立資料時一律寫入初始值,不存在留空的合法路徑」,設成必填讓
TypeScript 在編譯期直接擋下任何遺漏欄位的建立路徑,比事後補空值 fallback
更徹底。

初始值規則(補充裁決01之1「照你的提案做」):
- `sourceType` 依 `space` 對應(委派書只列值域沒給對應表,依各場域既有的
  中文描述直接對應,無歧義):修習所→practice、野採→forage、織光堂→work、
  聊解室→service、道藏→archive、收光→rest(委派書步驟三本身已明訂)。
  對應表存在 `SPACE_TO_SOURCE_TYPE` 常數。`alchemy`(知識煉金)沒有對應的
  space,是本輪額外支援的第七個值,目前沒有 UI 入口會寫入它。
- `traceLevel` 一律 `daily`。
- `traceStatus` 一律 `一般`——本輪只建欄位、只寫預設值,不實作任何依賴它
  的行為(收納/隱藏的實際操作留待痕跡卡片那一輪)。
- `viewCount` 一律 `0`。

三筆示範資料(`INITIAL_ENTRIES`)與所有建立新 entry 的路徑(`app/components
/DojoShell.tsx` 的 QuickAddModal、`app/timer/page.tsx` 的 `finishTimer()`)都
已依上述規則補齊四個欄位。

**本次不做**:`viewCount` 的計數與 `traceLevel` 的自動升級、`traceStatus` 的
任何行為——這些都需要持久化才有意義,`DojoEntry` 目前不持久化,整段延後。

### 二、收光的 `carryToDate` 與 `carryResolvedAt`

v1.0(《收光三選項與居所接續》)原本否決 `carryToDate`,因為當時只需要
「隔天」這一種情境,靠「昨天的收光紀錄」就能判斷。這次(v2.0)需要「未來
七天內任一天」,才真的需要一個獨立欄位記錄使用者選的是哪一天。

`lib/closing/notionFormat.ts` 的 `ClosingContent` 型別擴充:

```ts
export type ClosingContent = {
  space: "closing"; kind: "收光"; title: ClosingChoiceTitle; note?: string; date: string;
  privacy: "私人"; sourceType: "rest"; traceLevel: TraceLevel; traceStatus: TraceStatus; viewCount: number;
  carryToDate?: string;        // 僅 carry 時有值,明天起七日內
  carryResolvedAt?: string | null; // 僅「標記已處理」按下才寫入
};
```

**DB-14 現行「內容」欄位能不能承載這兩個新欄位**(委派書原本請回報這件
事,列選項讓擁有者裁決)——確認這不是真的需要裁決的架構問題:「內容」欄
本來就是自由格式文字,現在的做法就是把整包 JSON 序列化塞進去,加兩個新
的 JSON key 完全不需要開新庫、也不需要動 Notion schema。

`decodeClosingContent()` 對每個新欄位都做空值 fallback,不假設一定存
在——DB-14 裡已經有一筆用舊格式寫入的真實收光紀錄(就是驗證寫入路徑用的
那筆「收光紀錄-20260804」),沒有這輪任何新欄位,讀取時不能因為缺欄位就
壞掉。

`POST /api/closing` 新增 `carryToDate` 參數,`choice='carry'` 時必填,且驗
證必須落在「明天起七日內」(`isValidCarryToDate()`,用 `lib/date.ts` 既有
的 UTC-safe `addDays`/`toISODate`,不用「本地解析→`toISOString()`」那種會
在 UTC+8 位移一天的寫法——這正是批次建立那次教訓的同一個坑,這次一開始
就避開)。

**「帶回」這個選項的中文標題(`ClosingChoiceTitle`)維持「帶回明天」不
變**,即使使用者選的是三天後——委派書表格明訂三個固定中文標題,沒有說要
隨 `carryToDate` 變動,照原樣處理。UI 上把入口按鈕文字改標「帶回」(不是
「帶回明天」),避免跟「使用者可能選了別的日期」這件事矛盾;點下去之後展
開的是「明天／後天／MM-D」加星期幾的按鈕列(不用日曆元件、不用
`<select>`,全站禁用 `<select>`、日曆元件在手機上比按鈕慢)。

### 三、「標記已處理」

補充裁決01§一之3 裁決:**要有明確動作**,不採用「打開就算」。

新增 `PATCH /api/closing/[id]/resolve`:依 Notion page id 讀回該筆收光紀
錄,確認是「帶回」類型且尚未處理過,寫入 `carryResolvedAt = 現在時間`。
居所接續卡片上每張「帶回」卡片旁邊都有一顆「標記已處理」按鈕,按下成功後
直接把那張卡從畫面上移除(不用整批重新打 API)。

### 四、居所接續卡片改讀 Notion(不是記憶體裡的 DojoEntry)

`GET /api/closing/continuations` 的 Source A 邏輯全面改寫:

- **v1.0** 的做法:只查「昨天」一筆,判斷 `title === 帶回明天`,最多佔 1
  張。
- **v2.0**(補充裁決01§二)的做法:`carryToDate <= 今天 AND
  carryResolvedAt IS NULL`,依 `carryToDate` 由早到晚排序,**可佔滿三
  張**。

因為一筆「帶回」紀錄的 Notion 標題是「建立日」,不是 `carryToDate`,而
`carryToDate` 最遠可以是建立日 + 7 天,所以查詢邏輯改成往前掃
`CARRY_WINDOW_DAYS`(7)天內建立的收光紀錄,逐筆解出 `carryToDate` 再篩
選、排序、取前三張——不是只查一天。

卡片文字:有 `note` 就顯示 `note`,沒有就顯示「你想把這件事帶到今天」(拿
掉了 v1.0 版本文字裡的「昨天」,因為現在來源天數是變動的,不一定是昨
天)。硬性限制不變:最多 3 張、不足不補空位、零張整區不顯示、卡片過期仍
未消化繼續顯示不標示逾期、超過三張其餘不顯示不提示還有幾張。

Source B1(日上三更待產出)邏輯不變。

## §五、DB-17 的 `sourceId`(補充裁決01之5,選 A)

型),其他場域的痕跡要等各自有資料模型之後才能被提煉成牌——本輪不做

relation,這件事不需要程式碼配合)。
