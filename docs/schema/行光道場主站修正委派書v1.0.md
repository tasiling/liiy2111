# 行光道場主站 — 修正委派書 v1.0(2026-08-03)

依《三方協作規格書 v1.4》《UI 頁面結構書 v1.0》與《行光道場主站 — 修正委派書
v1.0》,修正四項問題,依委派書優先序處理。

## 一、批次建立的日期與天數 bug

### 排查過程與結論

回報現象:選「起始日 8/3、天數 14」,實際只建出 8/10–8/16、21 筆(7 天×3)。

逐段檢查:
- `app/api/sanko/batches/route.ts` POST 的日期展開邏輯
  (`dates = Array.from({length:days}, (_,i) => toISODate(addDays(new
  Date(startDate), i)))`)——用 node 直接跑同一段邏輯,`startDate="2026-08-03"`、
  `days=14` 得到的是正確的 8/3–8/16 共 14 個日期,不受伺服器時區影響(date-only
  的 ISO 字串依 ECMAScript 規格一律以 UTC 解析,`toISOString()` 也是 UTC,兩端
  一致,不會有委派書擔心的 UTC+8 位移)。
- `lib/date.ts` 的 `addDays`/`toISODate`——純毫秒運算,同上驗證無誤。
- `app/sanko/page.tsx` 的 `createBatch()`——用 Playwright 攔截瀏覽器實際送出的
  POST,選「起始日 8/3、14 天」後送出的 body 就是
  `{"startDate":"2026-08-03","days":14}`,跟畫面上的預覽(`8/3 – 8/16　14 天 ×
  3 篇 ＝ 共 42 篇`)完全一致。

以上路徑用當前這份程式碼都無法重現回報的症狀,找不到會產生「起始日晚 7
天、天數少一半」這個特定落差的邏輯錯誤。轉而檢視「這個結果模式還可能從哪裡
產生」:42 筆依序寫入 Notion 需要連續呼叫 42 次 `pages.create()`,原本
`withNotionRateLimit()` 只對 429/5xx 重試,任何沒有 HTTP status 的錯誤(網路
瞬斷、連線逾時等)都會在第一次失敗後直接放棄、不重試——如果批次寫入中途撞上
一次這類暫時性錯誤,就會出現「這批只成功一部分」的情況,而原本的完成訊息
(`已建立 {選的範圍},共 {選的天數×3} 篇{failed.length 筆失敗}`)是照抄「送出前
的參數」組字串,不是照「真正寫入成功的部分」组,容易讓人誤讀成「已經全部建
立,只是報了幾筆失敗」而忽略掉實際寫入的日期範圍已經跟預覽不同。

### 修正內容

1. `lib/notion/client.ts`:`withNotionRateLimit()` 的重試判斷從「只有
   429/5xx 才重試」放寬為「除了明確的 4xx(帶 status 但不是 429)以外都重
   試」——沒有 status 的錯誤(多半是網路層問題)本質上也是暫時性的,應該重試。
2. `app/api/sanko/batches/route.ts`:POST 回應新增 `expectedCount`(預期筆
   數)、`actualCount`/`actualStart`/`actualEnd`(依 `runBatch` 真正回報成功的
   jobs 算出,不是照抄請求參數)。
3. `app/sanko/page.tsx`:`createBatch()` 的完成訊息改用伺服器回報的實際結
   果組字串——全部成功時顯示「已建立 {實際範圍},共 {實際筆數} 篇」;有落差
   時改用 `.warn` 樣式明顯標示「只成功建立 X / Y 篇(實際範圍 ...),Z 篇失
   敗」,不會被誤讀成整批已完成。

### 驗證

用 Playwright 直接測試瀏覽器實際送出的 POST body 與畫面訊息:
- 選「8/3 起始、14 天」→ 預覽「8/3 – 8/16　14 天 × 3 篇 ＝ 共 42 篇」→ 送出
  body 為 `{startDate:"2026-08-03", days:14}`,與預覽完全一致。
- 模擬全部成功(mock 回應 `actualCount:42`)→ 顯示「已建立 8/3–8/16,共 42
  篇」。
- 模擬部分失敗(mock 回應 `actualCount:21, actualStart:"2026-08-10"`)→ 顯示
  「只成功建立 21 / 42 篇(實際範圍 8/10–8/16),21 篇失敗,請重新整理確認後
  再嘗試補建。」——這正好對應回報現象的數字組合,驗證新的訊息邏輯在這種情況
  下不會再誤導成「已完成」。

## 二、總覽台(/overview)行事曆破版

### 根因

`/overview` 掛在 `DojoShell` 的 `.dojo` 殼層底下(全站頁面皆如此),但這個頁
面本身沿用的是舊版 Tailwind 樣式(不是 `.dojo` 那套雛形樣式系統)。行事曆的
星期標頭與日期格用的是 Tailwind 的 `grid grid-cols-7` 工具類別,而
`app/dojo.css` 也定義了一個 `.dojo .grid { grid-template-columns: 1fr 1fr;
... }`(場域選單用的固定 2 欄版型)。兩者的類別名稱字面相同(`.grid`)但語意
完全無關;`.dojo .grid` 的選擇器特異度(兩個 class)比 Tailwind 的
`.grid`/`.grid-cols-7`(各一個 class)高,不論樣式表載入順序,`.dojo .grid`
一定會贏,導致 `grid-template-columns` 被覆蓋成 2 欄——這就是星期標頭「直向
堆疊」、日期格「單欄」的實際成因,用 Playwright 讀取 `getComputedStyle` 直接
驗證到 `gridTemplateColumns` 確實被算成兩欄。

同一頁的完成度儀表(`grid-cols-5`、`grid-cols-3`)也是同一個成因,雖然委派
書只點名行事曆,但這是同一頁、同一個 root cause,一併修正。

### 修正內容

1. 四處(星期標頭、每週日期格、完成度儀表兩個 grid)改用 inline style 直接
   指定 `display:grid` + `gridTemplateColumns: repeat(N, 1fr)`,不再用
   Tailwind 的 `grid` 類別名稱,避開跟 `.dojo .grid` 的碰撞。
2. `app/api/dashboard/route.ts`:`calendarFromDetails` 的 `標題` 改為優先顯
   示「更次」(晨光/日光/夜光),沒有更次值的舊式單筆明細退而顯示 Session 的
   項目用途,不再顯示 `d.明細編號`(`S-2026...` 這類編號)。
3. 同一天多筆任務維持全數渲染(這部分程式邏輯本來就對,只是視覺上被步驟一
   的破版蓋過去,肉眼看不出來)。
4. 有「更次」值的標籤,點擊改為連到 `/sanko?detailId={id}`(原本一律連到
   `/sessions?sessionId=`);`/sanko` 頁面新增讀取 `detailId` query,批次清單
   載入完成後自動捲動並用金色外框標示該筆,對齊 `/sessions` 既有的
   `highlightId + scrollIntoView` 做法。

### 驗證

Playwright 直接檢查 `getComputedStyle`:星期標頭與每週列的
`gridTemplateColumns` 修正後均為 7 個等寬欄位;標籤文字確認為「晨光/日光/夜
光」,找不到 `S-2026` 樣式的編號;從 `/overview?detailId=X` 對應的連結點進
`/sanko` 後,對應 slot 有金色外框樣式,確認捲動與標示都生效。

## 三、修習所改版:光念系統・五功法 → 光行五／光法五兩層

原本單層的舊版五功法系統已作廢(原本的五個名稱,含現已移除的第五項,一律不
再出現在程式碼、註解或畫面文案的任何地方),改為兩個獨立、可分別選填的標
籤層:

- **光行五**:凝光、煉光、**流光**(新增)、顯光、藏光——每日修行的運作方
  式。
- **光法五**:聚光、守光、隱光、祝光、映光——光行成熟後自然發展的應用。

兩層互相獨立:不填任一層都合法,可只標其一,也可同時標記兩層;不計分、不
解鎖、不累積等級。

### 改動範圍

- `lib/dojo/constants.ts`:原本的單一 `nen: NenKey | null` 欄位拆成
  `guangxing: GuangxingKey | null` 與 `guangfa: GuangfaKey | null` 兩個獨立
  欄位;`LIGHT_NEN` 拆成 `GUANGXING`/`GUANGFA` 兩個常數表。
- `lib/dojo/store.tsx`:`TimerConfig` 的 `nen` 改成 `guangxing`/`guangfa`
  兩個欄位;`startTimerWithNen()` 拆成 `startTimerWithGuangxing()` 與
  `startTimerWithGuangfa()` 兩個獨立入口。
- `app/components/DojoShell.tsx`(快速新增彈窗):原本一排「光念(選填)」改
  成兩排獨立的「光行(選填)」「光法(選填)」,各自都有「不特別標記」可以
  回到未選狀態。
- `app/components/EntryCard.tsx`:同時顯示光行標籤與光法標籤(有值才顯
  示,互不影響)。
- `app/page.tsx`(居所):`NenTodayStrip` 重新命名為 `GuangxingTodayStrip`,
  改為統計光行五個分類在目前 entries 裡的數量(光法不在居所首頁另外統計,
  維持跟原本單層版本相近的呈現份量)。
- `app/review/page.tsx`(回看):篩選從單一「光念」篩選列,改成「光行」
  「光法」兩排獨立篩選列,與既有的測頻篩選、搜尋一樣互不疊加(選其中一種,
  其他自動歸零)。
- `app/closing/page.tsx`、`app/dao/page.tsx`:原本單一 `e.nen` 標籤改成
  `e.guangxing`/`e.guangfa` 兩個獨立標籤(有值才顯示)。
- `app/timer/page.tsx`:原本一排「光念(選填)」改成兩排獨立的「光行(選
  填)」「光法(選填)」,並補上「不特別標記」的清除選項(原本這裡連舊版單
  層都沒有清除按鈕,這次一併補上,對齊委派書「不填完全合法」的要求)。
- `app/practice/page.tsx`(修習所):分頁從「身/心/靈修/念能/修行紀錄」
  (5 個)改為「身/心/靈/光行/光法/修行紀錄」(6 個);原本的單一「念能」
  分頁拆成「光行」「光法」兩個獨立分頁,各自可選一個項目、開始一段計時修
  行;「心」分頁下方新增第二排「知/情/意」子分頁(v1.1 就有的概念,這次正
  式做成 UI,預設「知」)。

### 驗證

## 四、收光復盤測頻新增強度欄位

新增「強度」(1–10),與既有「頻率」(0–1000 霍金斯量表)並列,規則完全比
照頻率:選填、可獨立清除、不計算平均、不畫進度條或長條圖、不做趨勢圖或期
間比較、居所不顯示、系統不自動推算數值。

### 改動範圍

- `lib/dojo/constants.ts`:`DojoEntry` 新增 `intensity?: number`,獨立於
  `freq?: number` 之外,undefined 代表尚未標記(不是 0——0 不是合法值,跟頻
  率的既有慣例一致)。
- `lib/dojo/hawkins.ts`:新增 `INTENSITY_MIN`/`INTENSITY_MAX`(1/10)與
  `formatFreqIntensityLabel(freq, intensity)`——集中處理委派書要求的精確顯
  示格式(兩者皆有:`500・愛 ・ 強度 7`;只有頻率:`500・愛`;只有強度:
  `強度 7`),避免各頁面各自拼字串產生細節落差。
- `lib/dojo/store.tsx`:新增 `setEntryIntensity(id, intensity | null)`,與
  既有的 `setEntryFreq` 各自獨立,互不影響對方欄位。
- `app/closing/page.tsx`:每筆片刻新增「強度」滑桿＋數字輸入,標記/清除方
  式與頻率完全對稱(各自的「標記頻率」「清除頻率」「標記強度」「清除強
  度」四個獨立按鈕);卡片頂端的合併標籤改用
  `formatFreqIntensityLabel()`。
- `app/components/EntryCard.tsx`:原本只顯示頻率的標籤,改用
  `formatFreqIntensityLabel()` 顯示合併格式,`showFreq` prop 同時控制頻率與
  強度是否顯示(居所頁呼叫時傳 `showFreq={false}`,兩者一起排除)。

### 驗證

Playwright 逐步操作收光頁面第一筆 demo 片刻:
- 初始:頻率／強度皆未標記,只顯示「標記頻率」「標記強度」兩個按鈕。
- 標記頻率 → 顯示「500・愛」。
- 再標記強度 → 顯示「500・愛 ・ 強度 5」,與委派書要求的格式完全一致。
- 清除頻率 → 顯示「強度 5」(頻率清除不影響強度)。
- 重新標記頻率、清除強度 → 顯示「500・愛」(強度清除不影響頻率)。

另外在收光頁面標記完頻率與強度後,用站內導覽(非 `page.goto()`,避免整頁
重載清掉非持久的 in-memory 資料)點回居所首頁,確認頁面全文不含「強度」也
不含「・愛」這類頻率標籤字樣——居所排除測頻的既有規則涵蓋新的強度欄位。
